# Сценарии Omega Rooms

Сервис помогает студентам и сотрудникам найти свободную аудиторию по времени, вместимости и оборудованию, затем забронировать выбранную.

## 1. Поиск свободной аудитории

**Участник:** студент или сотрудник университета.

**Цель:** найти аудиторию, подходящую для встречи в заданный интервал.

**Основной поток:**

1. Пользователь задаёт начало и конец встречи, число участников и нужное оборудование.
2. Сервис выбирает из каталога аудитории достаточной вместимости с этим оборудованием.
3. Сервис исключает аудитории, занятые собственными бронями или занятиями из внешнего расписания хотя бы на часть запрошенного интервала. Поиск проверяет весь заданный интервал, а не фиксированные часовые слоты; начало включено, конец исключён: `[начало, конец)`. Соседние интервалы без пересечения не конфликтуют.
4. Пользователь получает список подходящих свободных аудиторий с вместимостью и оборудованием каждой.

**Критерии приёмки:**

- **Дано** А-301 на 30 мест с проектором свободна, А-302 на 20 мест с проектором свободна, А-303 на 40 мест без проектора свободна; **когда** пользователь ищет аудиторию на 25 человек с проектором на интервал 14:00–15:00; **тогда** результат содержит А-301 и не содержит А-302 и А-303.
- **Дано** А-301 подходит по вместимости и оборудованию, но занята по внешнему расписанию на часть запрошенного интервала; **когда** пользователь выполняет поиск; **тогда** А-301 не предлагается.

- **Дано** А-301 подходит по параметрам и свободна с 14:00 до 15:00; **когда** в 14:05 пользователь ищет аудиторию на 14:05–15:00; **тогда** А-301 предлагается. Если запрошено 14:05–15:05, а с 15:00 начинается занятие или другая бронь, А-301 не предлагается.
- **Дано** А-301 занята до 14:00 и снова занята с 15:00; **когда** пользователь ищет её на 14:00–15:00; **тогда** соседние интервалы не исключают А-301 из результата.

## 2. Отказ при конкурирующей брони (ошибочный сценарий)

**Участник:** студент или сотрудник университета.

**Цель:** не получить ложное подтверждение, если найденную аудиторию уже забронировали.

**Основной поток:**

1. Пользователь находит свободную А-301 на интервал 14:00–15:00.
2. До подтверждения его выбора другой пользователь бронирует А-301 на пересекающийся интервал.
3. Первый пользователь пытается забронировать А-301 из своего результата поиска.
4. Сервис повторно проверяет занятость и отказывает с причиной «аудитория уже занята».

**Критерии приёмки:**

- **Дано** после поиска создана пересекающаяся бронь А-301 другим пользователем; **когда** первый пользователь подтверждает бронь А-301; **тогда** сервис отказывает с причиной занятости и новая бронь не создаётся.
- **Дано** два пользователя одновременно подтверждают бронь одной аудитории на пересекающиеся интервалы; **когда** запросы обрабатываются; **тогда** при отсутствии других причин отказа подтверждается ровно одна бронь — та, которая первой атомарно зафиксирована сервисом; вторая заявка получает `rejected` с причиной занятости, вторая бронь не создаётся. Проверка конфликта и фиксация собственной брони выполняются атомарно. Случайный выбор (`random`) не применяется; порядок поступления запросов не гарантирует порядок фиксации.

## Жизненный цикл Job

Job — одна заявка пользователя на бронирование выбранной аудитории и интервала. Состояние поиска в Job не входит. Разрешённые переходы:

- `created → checking`: заявка принята, началась проверка доступности аудитории.
- `checking → confirmed`: аудитория свободна, бронь создана.
- `checking → rejected`: обнаружен конфликт или нарушены правила бронирования; бронь не создана.
- `checking → failed`: проверку невозможно завершить из-за технической ошибки, например недоступного внешнего расписания; бронь не создана.
- `confirmed → completed`: забронированный интервал закончился.
- `confirmed → cancelled`: пользователь отменил бронь до начала интервала.

`rejected`, `failed`, `completed` и `cancelled` — конечные состояния. Любой переход, которого нет в списке, сервис отклоняет; в частности, нельзя подтвердить уже отменённую или отклонённую заявку.

## Что предложил ИИ

**Промпт:** «Для сервиса поиска и бронирования университетских аудиторий найди ещё три способа сломать основной сценарий: пользователь задаёт интервал, вместимость и оборудование, получает свободные аудитории и выбирает одну для бронирования. Не повторяй случай, когда аудиторию уже забронировал другой пользователь. Для каждого случая укажи ожидаемую реакцию сервиса».

| Предложение ИИ | Решение | Почему |
| --- | --- | --- |
| Пользователь задаёт интервал с концом раньше начала или в прошлом. Сервис должен сообщить об ошибке ввода. | Приняли | Иначе поиск или бронь получат бессмысленный интервал; это отдельный ошибочный сценарий для общего документа. |
| Внешнее расписание недоступно во время проверки. Сервис должен сообщить, что доступность не подтверждена, и не создавать бронь. | Приняли | Нельзя считать аудиторию свободной, если источник занятости не ответил; Job переходит в `failed`. |
| По заданным вместимости и оборудованию нет подходящих аудиторий. Сервис должен вернуть пустой результат и объяснить, что совпадений нет. | Приняли | Пустая выдача не должна выглядеть как сбой; пользователь сможет изменить параметры поиска. |
