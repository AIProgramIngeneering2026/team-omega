# ADR-0002: Идемпотентность создания Job

- **Дата:** 2026-11-15
- **Статус:** Принято для целевой архитектуры первой версии; реализация ещё отсутствует.

## Контекст и ограничения

Пользователь может дважды нажать кнопку бронирования, повторить запрос после
потери ответа или отправить несколько запросов одновременно. Отказ соединения
не сообщает, успел ли сервер сохранить Job и подтвердить бронь.

Повтор одного запроса не должен создавать новый Job или заново запускать Tool.
При этом два намеренно разных запроса нельзя объединять только потому,
что у них одинаковые параметры. Данные должны переживать перезапуск процесса.
Публичного удаления Job и политики истечения ключей в первой версии нет.

## Решение

Для `POST /jobs` требовать заголовок `Idempotency-Key`. Ключ действует
в рамках пользователя и операции создания Job. Он не является учётными
данными и не даёт доступ к чужой заявке.

HTTP API проверяет обязательность и формат ключа по OpenAPI: от 1 до 128
символов, шаблон `^[A-Za-z0-9._:-]+$`. Отсутствующий или неверный ключ даёт
`422 VALIDATION_ERROR` с `details[].field = Idempotency-Key`.

Dispatcher через Repository атомарно сохраняет Job в `created`, ключ
и исходное структурно валидное тело. Уникальное ограничение на пару
`(пользователь, ключ)` допускает только одну запись при конкурентных запросах.
Проигравший создание запрос читает сохранённое тело и Job и применяет
те же правила сравнения, что обычный повтор.

Ключ и тело хранятся вместе с Job на постоянном диске и переживают перезапуск.
В первой версии ключи не истекают и не освобождаются после отказа,
отмены или завершения Job.

### Поведение повторов

| Ситуация | Ответ и эффект |
| --- | --- |
| Новый ключ и структурно валидное тело | Создаётся один Job; первый запрос ожидает исхода по ADR-0001. |
| Тот же пользователь, ключ и тело | `200` с прежним `id` и текущим состоянием, включая `created` или `checking`; Tool повторно не вызывается. |
| Тот же пользователь и ключ, но другое тело | `409 IDEMPOTENCY_KEY_REUSED`, `details[].field = Idempotency-Key`; исходный Job не меняется. |
| Другой пользователь с тем же ключом | Независимый запрос; чужой Job не возвращается. |
| Ошибка структуры до сохранения Job | Новый Job не создаётся, новый ключ не занимает запись идемпотентности. Уже существующее соответствие не удаляется. |
| Структура верна, но бизнес-проверка отклонила параметры | `rejected` и причина сохраняются за ключом; исправленный запрос требует нового ключа. |

При сравнении тел учитываются значения полей JSON, а не байты запроса:
порядок ключей и пробелы JSON несущественны. Строки времени сравниваются
как переданы, без нормализации часовых смещений. Например,
`2026-11-20T14:00:00+05:00` и `2026-11-20T09:00:00Z` — один момент,
но разные значения тела для проверки идемпотентности.

После потери ответа или HTTP `5xx` клиент повторяет запрос с прежним ключом
и телом, чтобы узнать исход первоначального создания, а не создаёт новый ключ
вслепую. При известном `id` можно прочитать Job через GET.
Повтор после восстановления `PROCESSING_INTERRUPTED` возвращает тот же
`failed` Job; для новой попытки нужен новый ключ.

Идемпотентность не заменяет атомарную проверку занятости: запросы с разными
ключами создают разные Job, а конфликтующие брони отсеивает Repository.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
| --- | --- |
| Не защищаться от повторов | Один пользовательский запрос может породить несколько Job; потеря ответа делает результат неоднозначным для клиента. |
| Дедупликация только по телу запроса | Нельзя отличить сетевой повтор от намеренной новой попытки с теми же параметрами после отказа или отмены. |
| Хранение ключей только в памяти | Перезапуск теряет защиту именно тогда, когда клиент может повторять запрос с неизвестным результатом. |
| Постоянное хранилище с TTL ключей | Ограничивает рост данных, но требует согласованного окна повторов; после истечения тот же ключ способен создать новую заявку. Для первой версии эта семантика не выбрана. |

## Цена решения

- Клиент должен создавать ключ для нового намерения и сохранять его для повторов.
- Хранилище растёт вместе с историей Job и исходными телами; нужна постоянная
  уникальность и транзакционная запись соответствия.
- Для исправления параметров сохранённого Job нужен новый ключ, даже если
  исход завершился бизнес-отказом.
- Семантически равные моменты времени в разных строковых представлениях
  считаются разными телами и дают конфликт при одном ключе.
- Решение не защищает от повторного намерения с новым ключом и не гарантирует
  подтверждение брони; оно гарантирует один Job для одного пользовательского ключа.

## Условия пересмотра

Пересмотреть решение при появлении:

- публичного удаления Job или требований к удалению пользовательских данных;
- политики хранения истории и ограничений на объём данных;
- требования ограничить срок идемпотентности конкретным окном повторов;
- распределённого хранения, при котором нужно заново обеспечить атомарное
  создание Job и глобальную уникальность пользовательского ключа.

До изменения политики ключи не очищаются автоматически. Введение TTL,
удаления или нормализации тел требует отдельного решения и обновления OpenAPI,
поскольку меняет наблюдаемое поведение повторов.
