# Контракт Tool

Это контракт целевой реализации Omega Rooms на Python и FastAPI.
Исполняемого приложения пока нет; документ определяет требования к будущим Tool,
а не описывает уже реализованный интерфейс.

Основание: [архитектура](architecture.md), [OpenAPI](api/openapi.yaml),
[жизненный цикл Job](job-lifecycle.md) и [сценарии](requirements.md).

## Общие правила вызова

Tool — локальный компонент, выполняющий одну операцию предметной области.
Registry возвращает Dispatcher заранее зарегистрированный Tool по имени:
`SearchRoomsTool` или `BookingTool`. Dispatcher вызывает его напрямую
и получает результат после завершения операции. Сетевого протокола между ними нет.

Tool получает структурированные данные, а не HTTP-запрос: без заголовков,
Bearer-токена и `Idempotency-Key`. Зависимости Repository и ScheduleAdapter
предоставляются при создании Tool, а не пользователем в параметрах операции.
Tool не вызывает HTTP API, Dispatcher или Registry и не выбирает другой Tool.

Результат — успешное значение либо типизированный отказ, описанный ниже.
Это логический контракт: документ не предписывает конкретную Python-библиотеку
или способ реализации типов. Ожидаемые отказы не возвращаются строкой вместо результата.
HTTP-коды, сериализация и заголовки определяются HTTP API, а не Tool.

### Формат ошибки

Все описанные ошибки соответствуют
[`components.schemas.Error`](api/openapi.yaml):

```json
{
  "code": "ROOM_UNAVAILABLE",
  "message": "Аудитория занята на выбранный интервал",
  "details": [
    {
      "field": "room_id",
      "issue": "Есть пересечение с бронью или учебным занятием"
    }
  ]
}
```

- `code` — стабильный машинный код из OpenAPI.
- `message` — непустое понятное сообщение без стека вызовов и секретов.
- `details` — непустой список причин; `field` обозначает связанное поле,
  `issue` описывает нарушение.
- Для ошибки операции целиком, например отказа расписания или хранилища,
  используется `field: "$"`.

Tool не возвращает сырой ответ внешней системы или детали SQL.
ScheduleAdapter преобразует внешние ошибки в типизированные причины;
Tool передаёт их в согласованном формате.

## Кто проверяет параметры и управляет состоянием

| Участник | Ответственность |
| --- | --- |
| HTTP API | Аутентификация, корректность JSON, обязательные и лишние поля, типы, ограничения структуры из OpenAPI. В поиск передаёт проверенные структурные параметры; в бронирование — исходные строки времени, даже если их значения некорректны. |
| Dispatcher | Выбор Tool, создание Job и обработка идемпотентности через Repository, проверка владельца, начало `checking`, координация разрешённых переходов и сохранения исходов. Повтор с прежним ключом и телом не вызывает Tool заново. |
| SearchRoomsTool | Бизнес-проверка времени, фильтрация каталога и проверка доступности на весь интервал. |
| BookingTool | Бизнес-проверка времени, существования аудитории и занятости; запрос атомарного подтверждения через Repository. |
| ScheduleAdapter | Чтение и нормализация расписания; общий срок внешней проверки 5 секунд с первого обращения, включая повторы, для одного выполнения Tool. |
| Repository | Хранение, проверка ожидаемого состояния и атомарность изменений. Проверка собственных пересечений и запись подтверждения выполняются в одной транзакции. |

Неверная структура запроса отклоняется до вызова Tool и не создаёт Job.
Бизнес-проверки времени принадлежат Tool, даже если HTTP-валидация поиска
уже обнаружила часть нарушений. У поиска неверное время означает
`422 VALIDATION_ERROR`, у бронирования — сохранённый Job с `rejected`.
Поэтому контракт бронирования не требует заранее разобранных дат.

Получение, отмена и ленивое завершение Job выполняются Dispatcher и Repository,
не являются операциями этих двух Tool и не обращаются к расписанию при отмене.

## SearchRoomsTool

### Вход

| Поле | Тип и ограничения |
| --- | --- |
| `start_at` | Строка полной даты и времени ISO 8601 с `Z` или смещением `±HH:MM`. |
| `end_at` | Строка с теми же требованиями; момент строго позже `start_at` в UTC. |
| `participants` | Целое число не меньше 1. |
| `equipment` | Список уникальных непустых строк — кодов оборудования; пустой список разрешён. |

В начале проверки Tool однократно получает `now` с часов сервиса в UTC.
Требуется `start_at >= now`. Часовой пояс сервера или пользователя
автоматически не подставляется.

### Порядок выполнения

1. Проверить время относительно единственного снимка `now` по правилам выше.
   При некорректном времени вернуть `VALIDATION_ERROR` до чтения занятости.
2. Прочитать каталог и отобрать аудитории по вместимости и оборудованию.
   Если кандидатов нет, сразу вернуть `{"rooms":[]}` без обращения
   к ScheduleAdapter и без проверки собственных броней. Недоступность расписания
   в этом случае не влияет на результат.
3. Для непустого набора кандидатов проверить собственные подтверждённые брони
   через Repository и учебную занятость через ScheduleAdapter на всём интервале.
   При ошибке любой из этих проверок вернуть отказ, а не пустую выдачу.
4. Исключить занятые аудитории и вернуть оставшиеся, отсортировав по `id`.

### Результат и гарантии

Успех — объект `RoomSearchResult` с полем `rooms`: список объектов
`Room` с полями `id`, `name`, `capacity`, `equipment` из OpenAPI.
Порядок — по `id` по возрастанию; отсутствие совпадений — `{"rooms":[]}`.

Каждая найденная аудитория:

- имеет `capacity >= participants`;
- содержит все запрошенные коды оборудования;
- свободна от собственных подтверждённых броней и учебных занятий
  на всём полуоткрытом интервале `[start_at, end_at)`.

Соседние интервалы не конфликтуют. Неизвестный код оборудования
не является ошибкой, а не даёт совпадений.
Tool читает каталог и занятость, но не создаёт Job и не резервирует аудиторию.
Успешный поиск не гарантирует доступность при последующем бронировании.
Если проверка внешней занятости завершилась ошибкой, Tool не возвращает
частичную выдачу или успешный пустой список вместо ошибки.

### Отказы и отображение в API

| Код | `details[].field` | Причина | Ответ HTTP API |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | `start_at` или `end_at` | Некорректный формат, нет смещения, начало в прошлом или конец не позже начала. Для неверного порядка границ — `end_at`. | `422` |
| `SCHEDULE_TIMEOUT` | `$` | Исчерпан общий срок проверки расписания 5 секунд. | `504` |
| `SCHEDULE_INVALID_RESPONSE` | `$` | Ответ расписания нельзя корректно интерпретировать. | `502` |
| `SCHEDULE_UNAVAILABLE` | `$` | Источник расписания недоступен. | `502` |
| `STORAGE_UNAVAILABLE` | `$` | Нельзя прочитать необходимые данные хранилища. | `503` |
| `INTERNAL_ERROR` | `$` | Непредвиденная ошибка обработки; внутренние детали не раскрываются. | `500` |

## BookingTool

### Вход и предусловия

Dispatcher передаёт идентификатор `job_id` сохранённого Job в состоянии
`checking` и его неизменяемые параметры:

| Поле | Тип и ограничения |
| --- | --- |
| `job_id` | UUID существующего Job, для которого Dispatcher начал проверку. |
| `room_id` | Непустая строка идентификатора аудитории. |
| `start_at` | Исходная строка времени из запроса создания, в том числе пустая или некорректная. |
| `end_at` | Исходная строка времени из запроса создания с теми же правилами. |

Параметры берутся из сохранённого Job, а не из нового пользовательского
запроса к Tool. Пользователь не задаёт `state`, `owner_id` или результат проверки.
Job и ключ идемпотентности уже сохранены Dispatcher через Repository.

### Порядок выполнения

1. Получить один снимок часов `now` в UTC и проверить время:
   разбираемость строк, явное смещение, `end_at > start_at`
   и `start_at >= now`. Сравнения выполняются в UTC.
2. Проверить существование аудитории в каталоге.
3. Проверить учебную занятость через ScheduleAdapter на всём интервале.
   До успешных проверок времени и аудитории к расписанию не обращаться.
4. После чтения расписания запросить у Repository атомарную операцию:
   проверить ожидаемое состояние `checking`, повторно проверить собственные
   пересечения и в той же транзакции записать `confirmed` при отсутствии
   конфликта либо `rejected` с `ROOM_UNAVAILABLE` при собственном пересечении.
   Сетевой вызов не держит транзакцию записи SQLite.

При конфликте с учебным расписанием или собственной бронью результат —
`rejected`; вторая бронь не создаётся. При конкурирующих заявках
подтверждается только первая атомарно зафиксированная бронь.
Изменение внешнего расписания после его чтения не блокируется:
общей транзакции с университетской системой нет.

### Результат и сохранение

Логический результат — `confirmed`, `rejected` или `failed`.
Для `rejected` и `failed` обязательна ошибка `Error`; для `confirmed` её нет.

- `confirmed` возвращается только после атомарного подтверждения Repository.
- При конфликте собственных броней Repository уже сохраняет `rejected`
  с `ROOM_UNAVAILABLE` в транзакции проверки; Tool возвращает этот исход
  Dispatcher без повторного перехода состояния.
- При остальных бизнес-отказах или техническом исходе `failed` Tool возвращает
  причину Dispatcher, который сохраняет исход через условный переход Repository.
- HTTP API возвращает `201` с полным сохранённым Job, даже если он
  `rejected` или `failed`: создание заявки состоялось, бронирование — нет.
- Если исход нельзя надёжно сохранить, успешный результат не утверждается:
  HTTP API отвечает `503 STORAGE_UNAVAILABLE` либо `500 INTERNAL_ERROR`
  с ошибкой формата `Error` вместо Job. Последнее сохранённое состояние может остаться `checking`.

### Бизнес-отказы: `rejected`

| Код | `details[].field` | Причина |
| --- | --- | --- |
| `INVALID_TIME_FORMAT` | `start_at` или `end_at` | Строка не является корректной полной датой и временем, в том числе пустая строка. |
| `TIMEZONE_REQUIRED` | `start_at` или `end_at` | Дата и время заданы без явного смещения от UTC. |
| `INVALID_INTERVAL` | `end_at` | Конец не позже начала после приведения к UTC. |
| `START_IN_PAST` | `start_at` | Начало раньше единственного снимка `now` этой проверки. |
| `ROOM_NOT_FOUND` | `room_id` | Аудитории нет в каталоге. |
| `ROOM_UNAVAILABLE` | `room_id` | Интервал пересекается с учебным занятием или собственной подтверждённой бронью. |

### Технические отказы

| Код | `details[].field` | Результат |
| --- | --- | --- |
| `SCHEDULE_TIMEOUT` | `$` | `failed`: общий срок внешней проверки 5 секунд исчерпан. |
| `SCHEDULE_INVALID_RESPONSE` | `$` | `failed`: некорректный ответ расписания. |
| `SCHEDULE_UNAVAILABLE` | `$` | `failed`: источник расписания недоступен. |
| `INTERNAL_ERROR` | `$` | `failed`, если состояние удалось сохранить; иначе отдельная HTTP-ошибка `500`. |
| `STORAGE_UNAVAILABLE` | `$` | Типизированный отказ `Error`: нельзя прочитать или записать необходимые данные хранилища. HTTP API отвечает `503`; в `Job.error` отказ не сохраняется. |

`PROCESSING_INTERRUPTED` записывает Dispatcher при восстановлении оставшегося
без обработчика Job, а не BookingTool. Для сохранённого `created`
восстановление проходит через `checking`, затем `failed`.
Обрыв клиентского соединения сам по себе не прекращает обработку.
При отказе хранилища Dispatcher повторяет восстановление после его доступности.

Tool не перезапускает конечный Job. Поздний ответ расписания после `failed`
не создаёт бронь: Repository отклоняет переход не из `checking`,
не меняет состояние и занятость; событие записывается в журнал.
Это внутреннее нарушение предусловия, а не новый публичный код ошибки.

## Примеры

Примеры ниже показывают данные на границе Tool, а не полный HTTP-ответ Job.
Для первых четырёх примеров снимок часов — `2026-11-20T08:00:00Z`.

### Поиск: найдена аудитория

Вход:

```json
{
  "start_at": "2026-11-20T14:00:00+05:00",
  "end_at": "2026-11-20T15:00:00+05:00",
  "participants": 25,
  "equipment": ["projector"]
}
```

Результат при свободной А-301:

```json
{
  "rooms": [
    {"id": "A-301", "name": "А-301", "capacity": 30, "equipment": ["projector"]}
  ]
}
```

При отсутствии подходящих свободных аудиторий результат — `{"rooms":[]}`.
В обоих случаях HTTP API отвечает `200`, Job не создаётся.

### Бронирование: успех или конфликт

Вход при сохранённом Job в `checking`:

```json
{
  "job_id": "e1f84f96-ab65-4128-946a-08d6e64cf028",
  "room_id": "A-301",
  "start_at": "2026-11-20T14:00:00+05:00",
  "end_at": "2026-11-20T15:00:00+05:00"
}
```

Если аудитория свободна и подтверждение записано, результат — `confirmed`
без ошибки. Если обнаружено пересечение, результат — `rejected`
с `ROOM_UNAVAILABLE` и `field: "room_id"`; тело ошибки приведено выше.
После сохранения исхода HTTP API отвечает `201` с соответствующим Job.

### Бронирование: расписание не ответило

Для того же входа при истечении общего срока результат:

```json
{
  "state": "failed",
  "error": {
    "code": "SCHEDULE_TIMEOUT",
    "message": "Превышен срок ожидания внешнего расписания",
    "details": [
      {"field": "$", "issue": "Общий срок проверки расписания 5 секунд истёк"}
    ]
  }
}
```

После сохранения исхода HTTP API отвечает `201` с Job в `failed`.
Брони нет. Повтор `POST /jobs` с прежним ключом и телом возвращает
`200` с тем же Job без вызова BookingTool.
Для новой попытки необходим новый ключ и новый Job.
