# Проверка контракта Omega Rooms

## Условия проверки

Пользователи А и Б имеют разные действительные Bearer-токены. Аудитория
`A-301` существует и свободна, внешнее расписание доступно, если в строке
карты не указано иное. Текущее время сервиса для примеров —
`2026-11-20T08:00:00Z`.

Базовый запрос пользователя А:

```http
POST /jobs
Authorization: Bearer <токен пользователя А>
Content-Type: application/json
Idempotency-Key: omega-p2-booking-001

{
  "room_id": "A-301",
  "start_at": "2026-11-20T14:00:00+05:00",
  "end_at": "2026-11-20T15:00:00+05:00"
}
```

Интервал соответствует `[09:00, 10:00)` UTC. `J` в таблице обозначает
полный UUID Job, например `e1f84f96-ab65-4128-946a-08d6e64cf028`.

Тело `Job` содержит `id`, `room_id`, исходные `start_at` и `end_at`, `state`,
`created_at` и `updated_at`. Для `rejected` и `failed` обязательно `error`,
у остальных состояний оно отсутствует — [схема Job](api/openapi.yaml#L541).
HTTP-ошибки и `Job.error` имеют единую форму
`{code, message, details: [{field, issue}]}` — [схема Error](api/openapi.yaml#L596).
Ответ `201` подтверждает создание заявки, результат бронирования определяется
полем `state`.

## Проверка колодой К1–К10

| Карта | Статус | Ответ контракта |
| --- | --- | --- |
| **К1 Двойной клик** | Закрыта | А дважды отправляет базовый запрос с одним ключом и телом с разницей 100 мс. Создаётся один Job: первый запрос получает `201 Job`, повтор — `200 Job` с прежним `id` и текущим состоянием, в том числе `created/checking`, без новой проверки и второй брони. Гонку закрывают транзакция и уникальность пары «пользователь + ключ». Тот же ключ с другим телом даёт `409 Error`, `code=IDEMPOTENCY_KEY_REUSED`, поле `Idempotency-Key`; исходный Job не меняется. См. [POST /jobs](api/openapi.yaml#L155), [ключ идемпотентности](api/openapi.yaml#L424), [атомарность создания](architecture.md#L96). |
| **К2 Ответ потерялся** | Закрыта | А не получил ответ на создание и повторяет исходные ключ и тело. Сохранённая заявка возвращается как `200 Job` с тем же `id`; если исходная запись не состоялась, повтор создаёт Job с `201`. Обрыв соединения сам по себе не прекращает начатую обработку. Узнав `J`, клиент читает `GET /jobs/J` → `200 Job`; чтение не запускает новую проверку. При недоступной БД — `503 STORAGE_UNAVAILABLE` с полем `$`; результат выясняется после восстановления с прежним ключом, а не созданием заявки с новым. См. [POST /jobs](api/openapi.yaml#L155), [GET Job](api/openapi.yaml#L306), [StorageUnavailable](api/openapi.yaml#L801), [обработка независимо от соединения](architecture.md#L118). |
| **К3 Неизвестная операция** | Закрыта | При теле в пределах 65536 байт `POST /jobs/J/restart` получает `404 Error`, `code=ROUTE_NOT_FOUND`, поле `$`; `PUT /jobs/J` — `405 Error`, `code=METHOD_NOT_ALLOWED`, поле `$`, заголовок `Allow: GET`. Тело ошибок имеет форму `{code, message, details: [{field, issue}]}`. Маршрутизация предшествует аутентификации и проверке параметров пути. Операция не выполняется, Job не создаётся и не меняется, бронь не меняется, ключ не занимается. Это не `404 JOB_NOT_FOUND`, который относится к известным операциям с Job. Добавление поля `"operation":"restart"` в базовый запрос даёт `422 VALIDATION_ERROR`, поле `operation`, без Job и занятия ключа. При превышении размера тела приоритет имеет `413 PAYLOAD_TOO_LARGE` из К7. См. [общие правила](api/openapi.yaml#L13), [RouteNotFound](api/openapi.yaml#L662), [MethodNotAllowed](api/openapi.yaml#L677), [CreateJobRequest](api/openapi.yaml#L512), [ValidationError](api/openapi.yaml#L764). |
| **К4 Кривые параметры** | Закрыта | Отсутствующий `room_id`, число вместо `start_at`, пустой `room_id` или лишнее поле `state` дают `422 Error`, `code=VALIDATION_ERROR`, имя нарушенного поля в `details`; Job не создаётся, ключ не занимается. Невалидный JSON — `400 BAD_JSON`, неверный Content-Type — `415 UNSUPPORTED_MEDIA_TYPE`. Неверные строки времени в пределах 64 символов проходят бизнес-проверку: строка без смещения → `201 Job`, `state=rejected`, `error.code=TIMEZONE_REQUIRED`; пустая или неразбираемая строка → `rejected / INVALID_TIME_FORMAT`; конец не позже начала → `rejected / INVALID_INTERVAL`, поле `end_at`; прошлое начало → `rejected / START_IN_PAST`, поле `start_at`. В этих случаях брони нет, расписание не вызывается. Для поиска неверный интервал даёт HTTP `422`, без Job. См. [CreateJobRequest](api/openapi.yaml#L512), [создание](api/openapi.yaml#L155), [ValidationError](api/openapi.yaml#L764), [поиск](api/openapi.yaml#L55). |
| **К5 Воскрешение** | Закрыта | А повторяет создание Job в конечном состоянии `rejected`, `failed`, `cancelled` или `completed` с прежними ключом и телом: `200 Job` с тем же `id` и сохранённым результатом, без нового выполнения. Для новой попытки нужны новый ключ и новый Job; старый Job не перезапускается. Операции ручного подтверждения и перезапуска отсутствуют; передать `state` в создание нельзя — `422 VALIDATION_ERROR`, поле `state`, без нового Job. Обращение к отсутствующему маршруту перезапуска при теле в пределах лимита даёт `404 ROUTE_NOT_FOUND`, поле `$`, без изменения Job и брони (К3). См. [повторы POST /jobs](api/openapi.yaml#L155), [запрет выхода из конечных состояний и перезапуска](job-lifecycle.md#L64), [GET без перезапуска](api/openapi.yaml#L306). |
| **К6 Отмена** | Закрыта | А вызывает `POST /jobs/J/cancel`, пока Job в `checking`: `409 Error`, `code=INVALID_JOB_TRANSITION`, поле `state`; Job и занятость командой не меняются, проверка не отменяется. Для `confirmed` строго до `start_at` — `200 Job` со `state=cancelled`, интервал освобождается атомарно. При `now == start_at` и до конца встречи — `409 CANCELLATION_TOO_LATE`, поле `start_at`. После конца Job сначала становится `completed`, затем отмена даёт `409 INVALID_JOB_TRANSITION`. Повтор отмены `cancelled` также даёт `409`. Потерянный ответ выясняется через GET. См. [POST cancel](api/openapi.yaml#L340), [запрещённые переходы](job-lifecycle.md#L64). |
| **К7 Огромный вход** | Закрыта | А отправляет `POST /rooms/search` с 100000 различными непустыми кодами оборудования либо `POST /jobs` с `room_id` длиной 100000 символов. Оба тела превышают 65536 байт и получают `413 Error`, `code=PAYLOAD_TOO_LARGE`, `details: [{field: "$", issue: "Максимальный размер тела запроса — 65536 байт"}]`, с непустым `message`. Лимит 64 КиБ включает пробелы JSON; ровно 65536 байт допустимы. Проверяется фактически прочитанный объём, в том числе без Content-Length; чтение прекращается при превышении. Отказ предшествует разбору JSON, маршрутизации, аутентификации и другим проверкам, применяется также к повторам. Job не создаётся, существующий Job и бронь не меняются, ключ не занимается. Для тела в пределах лимита действуют структурные ограничения: `equipment` — не более 100 элементов, каждый код и `room_id` — не более 128 символов, `start_at` и `end_at` — не более 64. Например, 101 короткий уникальный код или `room_id` из 129 символов дают `422 VALIDATION_ERROR` с полем `equipment` или `room_id`; Job и бронь не создаются, ключ не занимается. См. [лимит и приоритет проверок](api/openapi.yaml#L13), [PayloadTooLarge](api/openapi.yaml#L698), [RoomSearchRequest](api/openapi.yaml#L454), [CreateJobRequest](api/openapi.yaml#L512), [ValidationError](api/openapi.yaml#L764). |
| **К8 Чужой или несуществующий id** | Закрыта | Б запрашивает `GET /jobs/J` или `POST /jobs/J/cancel` для заявки А, затем повторяет с несуществующим корректным UUID. В обоих случаях одинаковые `404 Error`, `code=JOB_NOT_FOUND`, поле `job_id`, без раскрытия чужого состояния и без изменения брони. Некорректный UUID даёт `422 VALIDATION_ERROR`, поле `job_id`; отсутствующий или недействительный токен — `401 UNAUTHORIZED`, поле `Authorization`. Ключ идемпотентности изолирован по пользователям и не открывает чужой Job. См. [JobNotFound](api/openapi.yaml#L786), [JobId](api/openapi.yaml#L416), [Unauthorized](api/openapi.yaml#L730), [IdempotencyKey](api/openapi.yaml#L424). |
| **К9 Перезапуск сервера** | Закрыта | Сбой происходит, когда сохранённый Job находится в `checking` — аналог `running` в карте. До приёма новых запросов после запуска он переводится в `failed` с `error.code=PROCESSING_INTERRUPTED`; брони нет. Сохранённый `created` сначала проходит в `checking`, затем в `failed`, без вызова Tool. `GET /jobs/J` и повтор создания с прежним ключом возвращают `200` с тем же Job. Новая попытка требует нового ключа. Уже атомарно сохранённая бронь `confirmed` не превращается при восстановлении в `failed`; конечные состояния не перезапускаются. Недоступное хранилище даёт `503 STORAGE_UNAVAILABLE`, а не успешное восстановление. См. [восстановление после запуска](architecture.md#L112), [переходы при восстановлении](job-lifecycle.md#L42), [схема Job](api/openapi.yaml#L541), [StorageUnavailable](api/openapi.yaml#L801). |
| **К10 Внешний сервис** | Закрыта | Расписание молчит 30 секунд: общий срок проверки ограничен 5 секундами с первого обращения, включая повторы. `POST /jobs` возвращает `201 Job`, `state=failed`, `error.code=SCHEDULE_TIMEOUT`, поле `$`; брони нет. Неразбираемый ответ или переименованное обязательное поле дают `failed / SCHEDULE_INVALID_RESPONSE`, невозможность соединения — `failed / SCHEDULE_UNAVAILABLE`. Клиент читает этот результат через `GET` → `200 Job`. Поздний ответ после `failed` не создаёт бронь и не меняет результат. Поиск не создаёт Job: таймаут → `504 SCHEDULE_TIMEOUT`, некорректный ответ или недоступность → `502` с соответствующим кодом Error; успешная пустая выдача не подставляется. См. [POST /jobs](api/openapi.yaml#L155), [ошибки поиска](api/openapi.yaml#L55), [переход checking → failed](job-lifecycle.md#L45). |

### Итог проверки колодой

Все десять карт К1–К10 закрыты проверенной версией контракта.
Для К3 OpenAPI определяет ошибки неизвестного маршрута и неподдерживаемого
метода; для К7 — общий предел тела, ограничения полей и ответы при превышении.
Отчёт учитывает обновление OpenAPI в коммите `4eafc06` ветки этого PR.
Проверка относится к описанному контракту и не подтверждает наличие реализации API.

## Что предложил ИИ

Аудит выполнен Codex по полным текстам API, колоды, архитектуры,
жизненного цикла и требований из проверенной версии.
Постановка для дополнительной проверки:

### Промпт

> Сыграй атакующего на контрактном покере для Omega Rooms. Используй
> переданные openapi.yaml, architecture.md, job-lifecycle.md,
> requirements.md и колоду К1–К10. Найди ещё три конкретные ситуации,
> для которых эти документы не определяют однозначный результат.
> Не повторяй уже найденное отсутствие ответов на неизвестный HTTP-маршрут
> и большой вход. Для каждой ситуации приведи запрос или порядок событий,
> укажи, какого правила не хватает, и предложи уточнение отдельно от ответа
> действующего контракта. Не считай пробелом поведение, уже описанное
> в архитектуре или жизненном цикле. Контракт не редактируй.

### Находки и решения

Решения ниже относятся к предложениям изменить контракт в рамках этой задачи.
Все три находки записаны в отчёт; предложенные новые правила не внесены
в API и не используются в качестве ответов на карты.

| Находка ИИ | Чего не хватает и предложение | Решение |
| --- | --- | --- |
| **ИИ-1. Повторяющиеся имена полей JSON.** А отправляет `{"room_id":"A-301","room_id":"A-302","start_at":"2026-11-20T14:00:00+05:00","end_at":"2026-11-20T15:00:00+05:00"}` с новым ключом. | [CreateJobRequest](api/openapi.yaml#L512) описывает уже разобранный объект, [BadJson](api/openapi.yaml#L715) — невалидный JSON. Правило для повторяющихся имён не задано: нельзя определить, какая аудитория попадёт в заявку и какое тело будет сравниваться при повторе. **Предложение:** явно отвергать дубли имён до создания Job и занятия ключа, с согласованной HTTP-ошибкой в формате Error. | **Изменение контракта не приняли в эту задачу:** она ограничена проверкой; новое правило разбора JSON потребовало бы дополнения API. Неоднозначность зафиксирована как находка, без утверждения, что она устранена. |
| **ИИ-2. Два разных заголовка Idempotency-Key в одном запросе.** А передаёт одновременно `Idempotency-Key: omega-p2-booking-001` и `Idempotency-Key: omega-p2-booking-002`. | [IdempotencyKey](api/openapi.yaml#L424) задаёт формат одной строки, но не правило обработки нескольких одноимённых заголовков. От выбора первой строки, последней или объединённого значения зависит занятый ключ и результат повтора. Нельзя автоматически приписать этому случаю описанный `422` для неверной одиночной строки. **Предложение:** требовать ровно одно значение и явно описать отказ до создания Job. | **Изменение контракта не приняли в эту задачу:** добавление ограничения числа заголовков выходит за рамки отчёта. Записали конкретную неоднозначность отдельно от уже закрытой К1; новый код ответа не назначали. |
| **ИИ-3. Неполные данные расписания при корректном JSON.** На проверку А-301 на 14:00–15:00 источник отвечает HTTP 200, но данные покрывают только 14:00–14:30 либо запись об А-301 отсутствует. | [Описание поиска](api/openapi.yaml#L55) и [создания](api/openapi.yaml#L155) требуют проверки занятости, но не определяют, как отличить подтверждённо пустую занятость от неполноты ответа источника. Ошибка синтаксиса из К10 здесь отсутствует. **Предложение:** определить критерий полноты внешнего ответа и явно отказывать в подтверждении при неполных данных, сохранив допустимость достоверно пустого расписания. | **Изменение контракта не приняли в эту задачу:** критерий полноты требует согласования формата внешнего расписания и дополнения правил адаптера/API. В отчёте отмечена неопределённость; отсутствие данных не объявлено доказательством свободной аудитории. |

При обновлении отчёта по замечаниям ревью изменён только этот файл;
использовано уже внесённое в ветку PR обновление OpenAPI.
Три дополнительные находки ИИ остаются неустранёнными; они не подменены
предполагаемым поведением FastAPI или предлагаемыми решениями ИИ.
